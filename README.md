# dsh-enhanced-team-mode

在开启「启用智能体团队协作」的会话里，于用户发起独立任务时向主模型注入一次协作指令；同时提供一个插件自带的协作手册 Skill，和一个只影响本插件派发成员的模型设置页。团队里有三档成员：能力型执行（Atlas）、讲解席（Mentor）与审计席（Argus），主对话称 leader。调研是任务板上的独立任务，由能力型执行成员写研判契约；审计席从需求提出起后台跟随，交付时仍做终审，两件事由设置页两个开关分别启停。

插件不创建成员、不拦截工具、不新增开关。成员由主对话通过原生 subagent / subagent_fork 工具创建，模型授权校验仍在宿主工具层。

## 组成

| 部分 | 位置 | 作用 |
| --- | --- | --- |
| 一次性注入 | src/inject/ | 根会话首个独立任务、以及用户明确另起任务时，注入一次协作指令 |
| 核心职责单一来源 | src/inject/instruction.js | 静态职责、审计职责四变体、三项固定检查与讲解协议在这里定义一次，注入与 Skill 逐字引用 |
| 协作手册 Skill | skills/team-mode-collaboration/SKILL.md | 详细流程（任务卡与调研、派发、任务板、审计巡检与终审、讲解席、通信、长任务、模型设置），按需加载 |
| 设置模块 | src/settings/ | 三个模型档（审计、能力型执行、讲解）各一组 provider/model/reasoningEffort，加两个审计开关；空串表示跟随 DSH 默认 |
| 派发路由 | src/dispatch/ | 按当前会话授权解析路由，写进注入指令 |
| 设置页（浏览器半） | lib/client.js | 插件页里的审计（Argus）/能力型执行（Atlas）/讲解（Mentor）模型选择，以及两个审计开关 |
| 判定测试 | test/、tests/ | 单位、模块、集成三层 |

## 安装

未包含在本仓库的自动流程里。手工安装到某个 profile 时按下面的形状放文件，并在该 profile 的插件清单里加入一行（id 是 entry id，也是设置页命名空间；name 才是包名，两者可以不同）：

    <profile>/node_modules/dsh-enhanced-team-mode/   ← 本目录内容
    cordis.patch.yml 里已声明插入行：
        - insert:
            - id: team-mode
              name: 'dsh-enhanced-team-mode'

包的清单已经声明了浏览器半与包内技能：

    "exports": { ".": "./index.js", "./client": "./lib/client.js" }
    "dsh": { "bundle": { "patch": "./cordis.patch.yml" }, "client": { "platform": "web" } }
    "files": [ "index.js", "src", "lib/client.js", "skills", "cordis.patch.yml", "package.json", "README.md" ]

本次交付没有安装到任何 profile，也没有改全局配置。

## 设置

入口：插件页 → 本插件 → 配置区（槽位 plugins.bundle.config，按包名 key）。

| 字段 | 含义 |
| --- | --- |
| 审计模型 | 独立审计成员 Argus（最多 1 名，实例名 argus）的默认模型，可与任一执行模型相同 |
| 能力型执行模型 | 调研、设计、实现等需要较强能力的执行成员（Atlas，最多 3 名，实例名 atlas-1 到 atlas-3）共用此默认模型 |
| 讲解模型 | 讲解席 Mentor（1 名）使用此默认模型，讲清项目机制、接口与实现路径；建议与执行席同级 |
| 后台持续审计 | 开关，默认开。开启时审计席从需求提出起跟随所有活跃席位，按任务覆盖并轮转 |
| 交付终审 | 开关，默认开。开启时每个交付物由审计席判定通过、退回或阻塞；通过前不得报告完成 |

- 三个模型档都可以选择「跟随 DSH 默认」：此时派发不传 provider 与 model，成员继承父路由。
- 两个审计开关决定审计席是否存在：任一开启即 1 名（团队上限 5），都关则 0 名（上限 4）。都关时审计模型档置灰，已保存的选择保留、暂不生效，不产生孤儿配置。
- 旧版本配置没有 mechanical 字段时按「跟随 DSH 默认」兼容，不需要迁移；没有 auditMode 段时按两个开关都开处理，同样零迁移。mechanical 这个存储键保留，界面显示为讲解模型。
- 候选来自宿主已注册的模型目录；派发前再按当前会话的授权列表校验一次。
- 只影响本插件派发的新成员。已有成员保留当前模型，不为了换模型而重建。
- 不改主对话模型、普通子代理或 DSH 的全局默认模型。
- 显式选择的路由不可用时（未注册、未公布、未授权、别名歧义），报错并说明原因，不静默换用其他模型。
- 派发时省略 provider 与 model 会继承父路由，这是宿主契约（subagent 的 resolveChildAgentOptions 用父选项兜底），不会失败。所以"跟随默认"就靠省略实现，而漏传参数不会报错，只会悄悄用父模型。

## 按需查询当前设置

一次性注入的路由是任务开始时的快照。任务进行中改了设置，已注入的指令不会跟着变。为此插件提供一个只读工具：

    team_model_routes

- 新建成员之前调用它，得到按当前配置与当前会话授权重新解析的路由。
- 复用已有成员不需要调用，也不该传路由参数。
- 它与团队开关同生灭，普通会话里不出现。
- 它只读：不创建成员、不改状态、不拦截任何现有工具；授权仍由原生 subagent 工具裁决。
- 局限：是否调用由模型按指令决定，插件无法强制。若模型跳过调用并漏传参数，成员会继承父路由而不是失败——这正是需要这条指令的原因，也不能声称漏传一定会被拒绝。

## 协作手册 Skill

名称：team-mode-collaboration，随插件注册（ctx.skills.register）。

- 一次性注入只给六条职责边界和一句指针；详细流程在 Skill 里，需要时加载一次，不要逐轮重复加载。
- 两者共享核心职责：六条文本只在 src/inject/instruction.js 定义一次，Skill 逐字引用，tests/integration/skill.test.mjs 做漂移守卫。
- 限制：注册发生在插件加载时，Skill 从那时起一直可见，不随团队开关显隐。宿主不会自动扫描插件包里的 skills 目录（bundledSkillDir 是宿主侧单根配置，改它属于全局设置，本插件不碰），所以这里用运行时注册。技能正文自己声明只在该会话开启团队协作时适用。

## 注入行为

- 触发：根会话（origin 不是 subagent）某一轮的第一步，领取到 source.kind 为 user 的真人消息。
- 首次：每个会话的首个独立任务自动注入一次。
- 之后：只有用户明确表达另起独立任务（高置信度自然语言）才再注入一次。含糊、意见调整、追问、返工、队友消息、自动续跑、压缩与恢复都不重新注入。
- 去重依据由会话投影从日志重放：重启、恢复、重入不会重复注入。
- 模式关闭：不再新增注入。历史里已注入的指令仍留在会话中，插件无法删除或改写它，也不承诺它会自动失效。
- 压缩：可能把已注入的指令扫进 checkpoint 并从表面移除。按当前约定不补发。

## 限制与未验证项

1. 人数上限、角色分工、两个审计开关与讲解席都靠提示词约束，没有工具层硬拦截。
2. 任务卡与研判契约同样是提示词约定。插件不校验契约是否存在、字段是否齐全，也不阻止协调者跳过调研直接派发；契约的执行依赖模型遵循度。
3. 插件不自建成员：授权校验发生在原生 subagent 工具层；插件侧只是按同一份会话授权解析路由并写进指令，不构成授权绕过。
4. 主对话是否调用 team_model_routes、是否照结果传参，属于模型遵循度，测试无法保证。漏传参数不会失败：成员继承父路由（见上）。
5. 任务内改设置后，已注入的指令文本不会更新；新成员是否用上新值，取决于模型按指令调用查询工具。
6. 真机验证的范围仅限隔离 profile：设置页渲染、保存落盘、重启回显、插件详情页配置卡片与宿主 Menu 下拉，都已在
   **team-dev 隔离 profile**（`dsh --profile team-dev`，本地 file: 依赖 + 重启后实测）验过。desktop profile 当前跑的是
   4036a6d 旧版本，**新版本尚未在 desktop 验证**；desktop 的安装与验证不在本仓库的交付范围内。
7. 设置页的实时生效路径（Volatile 配置在保存后的传播时序）只在 team-dev 做过一次性回环验证：保存 → 配置写入
   `cordis.patch.yml` → 完全重启实例 → 重新打开设置页回显一致。运行中不重启的传播时序仍未验证，当前实现按
   「插件重新加载后生效」的语义处理。
8. 无 allowlist 时只允许父路由，这是宿主的规则，插件照此呈现，不提供绕行方式。
9. 三项审计固定检查同样是提示词约定：宿主能力对照要求的 app.asar 路径与行号、重复实现清单、导入边界结论都由审计席自行取证，插件不校验证据是否存在，只规定缺证据的判定无效。
10. 两个审计开关是插件配置，注入按加载时的配置取值：任务进行中改开关，已注入的指令不会跟着变，要等下一次注入或重新加载。
11. 讲解席只读、只解释，不产出交付物；插件不校验讲解质量，也不记录讲解内容。
12. 交互结构取舍：本插件收起态直接是两行选择器（模型 / 思考强度），宿主 ModelSelect 是单一触发按钮、点开菜单后再选「模型 / 推理等级」两级。这是按用户要求做的上层两个选择器，视觉语言（行高、配色、圆角、阴影、字体层级）对齐宿主，结构不逐像素复刻，属于有意的取舍。
13. 箭头优先用宿主图标组件（`IconChevronDownOutlineRegular`，取不到时退回 `IconChevronDownOutline14`），依赖基线模块 `@deepseek-ai/dsh-client-ui-primitives`；该模块不可用时退回字符箭头，不阻塞渲染。
14. 席位英文名（leader / Atlas / Mentor / Argus）是提示词约定，不是宿主的 agent 名：主对话的实际 name 由宿主赋予，插件不创建成员、不改 agent 名；子成员 name 只用 atlas-1 到 atlas-3、mentor、argus。名字只体现气质，不固定分工。

## 回退

1. 在 profile 的插件清单里停用或删除本插件的插入行，重载 DSH。
2. 关闭「启用智能体团队协作」可停止注入，但不会清除历史里已注入的指令。
3. 设置保存在 profile 配置里，删除本插件的配置段即可回到「三档模型都跟随默认、两个审计开关都开」。
