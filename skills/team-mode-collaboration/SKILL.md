# 团队模式协作手册

一次性注入只给职责边界；这份手册给可执行的流程。研判契约、派发、审计循环或交接格式拿不准时读它，同一轮里不要重复加载。

## 何时适用

- 当前会话已开启「启用智能体团队协作」。
- 你正在承担协调者角色，需要把任务分给执行成员或审计成员。
- 模式关闭时不要按本手册行事：插件不会新增注入，也不保证历史里的旧指令自动失效。

## 团队结构

- 能力型执行成员最多 3 名，调研、设计细节、实现和测试共用这 3 个席位。
- 机械执行成员最多 1 名，独立审计成员最多 1 名，均不计入能力型执行席位。主对话不计入，整个团队最多 5 名 teammate。
- 席位是上限，不是开工配额。空闲成员也计入席位。
- 不得以额外子代理变相扩充同一团队的执行席位。

## 从任务到派发

开工前先完成阶段 0 研判（见「开工研判」一节），契约批准后再进入下列步骤。

1. 判断任务是否需要并行：互不依赖的部分才能同时开工。
2. 先定责任人，再启动。每项任务写清目标、范围、验收标准和交付格式；范围与验收标准取自研判契约，契约覆盖不到的部分先走变更请求。
3. 跨成员协作时，先划分互不重叠的写入范围；共享文件或同一代码区域先排定归属。
4. 有依赖的任务串行：把后继任务留在队列，等前置完成再派。
5. 派发前检查现有成员与占用：能交回已有成员就不新建。
6. 成员交付后回到可分配状态，同角色的下一项任务优先交回它。

## 任务板

- 常规进度（待办、进行中、待审计、完成）写在任务板，不作为消息发送。
- 状态更新用读到的当前 revision 做比较并交换；过期就重读，不要覆盖别人的更新。
- 任务写 write_scopes（工作区相对路径前缀）以便重叠提示；它只是提示，不阻止操作。
- 每项任务的身份与成员身份分开记录；同一成员可以先后承担多项任务。

## 开工研判（阶段 0）

审计席在派发实施任务之前交付研判契约。它回答两件事：问题是什么，做到什么算解决。契约未获批准，不进入「从任务到派发」的后续步骤。

正文落盘 .reports/recon/<任务号>.md；任务板的任务描述只记文件路径与一句话结论，不贴正文。

| 字段 | 要求 |
| --- | --- |
| 问题陈述 | 谁在什么情境下遇到什么可观察的错误行为；现象与推测分开写，推测必须标注为推测。 |
| 范围与非目标 | 这次改什么、明确不改什么；非目标用于挡住顺手扩张。 |
| 验收标准 | 逐条可判真假，写命令、观察点与期望输出；不写「体验正常」这类无法核对的表述。 |
| 风险 | 最脆弱的假设，可能被牵连的模块、配置或环境。 |
| 未知项 | 尚未确认的事项清单，每条附确认方式；终审时逐条回答。 |
| 证据位置 | 文件与行号、命令输出路径、截图或日志路径。 |

- 批准：范围与非目标、验收标准由协调者批准；问题陈述、风险、未知项与证据位置由审计席自行发布，协调者不改写问题陈述。
- 接单确认：执行成员接单时必须先回复「接受」或「质疑」。质疑只针对验收标准不可执行或范围与非目标不成立，并附证据位置；由协调者裁决。没有回复不得开工。
- 变更：实施中发现契约有误，提交变更请求，不静默偏离。契约末尾保留变更记录表，列出时间、变更项、提出者、裁决与理由；终审以最终版为准。
- 阻塞预算：研判阻塞不超过一个回合。超时先交「初步契约 + 未知项」并放行，未知项在终审前补齐。
- 豁免：纯调研任务以任务产出代替契约；按指令执行的机械任务不要求完整契约，但任务卡必须写清范围与验收标准。
- 禁令：审计席不得成为实施者，不代修，不改交付物。为研判而读项目文件、跑复现、查日志、读宿主实现属于允许动作。
- 固定检查（阶段 0）：A 宿主能力对照、B 重复实现、C 导入边界，逐项给出结论与证据，判定标准与阶段 N 相同，缺任一项判定无效。

## 审计固定检查（阶段 0 与阶段 N）

审计席在阶段 0 与阶段 N 都要执行下列三项固定检查，逐项给出结论与证据；缺证据的判定无效：

A. 宿主能力对照：对每一处手写实现，列出它解决的问题，检索宿主是否已有等价能力（组件、工具、API、配置机制）；结论三选一并附宿主证据（app.asar 内路径与文件:行号）与判定理由：可直接复用 / 无法复用 / 复刻（标注「复刻，原因：…」）。可直接复用另须写明接入方式四要素：宿主能力名称、引用入口（包名，或 id/client 形式的子路径）、是否需要额外声明（inject 的服务名；dsh.client.external 是否要加；是否为 platform-singleton（module-table 基线）模块，该类无需 dsh.client.external 声明）、版本或来源约束。三个分支缺证据或缺理由即判定无效，不默认成立；可直接复用缺任一要素同样无效。行号来源优先引宿主 app.asar 内 src/*.ts(x) 源码；只有该项目无源码可引时才引构建产物，并注明产物已压缩、行号没有定位意义。

B. 重复实现检查：同一逻辑在插件内是否存在多处实现（如重复的格式化、校验、状态读取、路径拼接），列出重复点、位置与合并建议。

C. 导入边界检查：是否只经公开入口引用；是否存在跨层深引用内部文件；是否有未声明的运行时依赖；是否存在循环依赖；所有宿主服务访问是否都在 inject 声明中。

- 阶段 0：三项结论与证据并入研判契约的「证据位置」；缺证据的判定无效，不允许用一句「宿主没有」了事。
- 阶段 N：逐项复核实施者的结论与证据位置。宿主能力对照三个分支都要有宿主证据与判定理由；可直接复用另须给出接入方式四要素（能力名称、引用入口、额外声明、版本或来源约束），复刻须写出原因。
- 判据：宿主能力对照三选一（可直接复用 / 无法复用 / 复刻），缺证据或缺理由即无效，可直接复用缺接入方式四要素同样无效，不默认成立；重复实现列出重复点与合并建议；导入边界逐项回答上面五个问题。
- 行号来源：优先引 app.asar 内 src/*.ts(x) 源码；只有该项目无源码可引时才引构建产物，并注明产物已压缩、行号没有定位意义。
- 接法示例：ctx.remote.session 的每个命名空间是平级独立 Service，只声明 remote 会抛 cannot get property "remote.session" without inject；@deepseek-ai/dsh-client-ui-primitives 是 platform-singleton（module-table 基线）模块，不需要 dsh.client.external 声明。

## 审计常驻循环

审计席从开工研判到交付终审是同一身份的两个阶段：阶段 0 见上一节，阶段 N 见本节。

- 审计成员在派发之前启动，先交研判契约，之后与执行过程并行在场，贯穿开发过程。
- 阶段 0 未获批准，不派发实施任务。
- 阶段 N 按最终版契约逐条核对，结论注明任务 id 与 revision，并核对变更记录与实际改动是否一致。
- 固定检查（阶段 N）：A 宿主能力对照、B 重复实现、C 导入边界。三个分支都要有宿主证据与判定理由；可直接复用另核接入方式四要素（能力名称、引用入口、额外声明、版本或来源约束），缺任一项判定无效。
- 巡检点：关键接口成形、首个实质性交付、出现风险或方案变更时。
- 审计成员空闲时可低频等待，不需要主对话保持前台，也不要用轮询或 sleep 等它。
- 发现问题直接交给对应实施者；需要你做决定或协调时，它才通知你。
- 交付后由同一审计成员终审，返工后由它复审。复审通过前不得报告完成，不另建审计成员。
- 审计成员不代修，退回的修改由原实施者完成。

## 通信与简报

只在以下情形发消息：阻塞、需要决策（含研判契约批准与变更裁决）、交付、审计退回。

简报格式：结论、证据位置（文件与行号或命令输出路径）、下一步。不要把完整日志贴进消息。

任务板上的状态变化不产生消息；需要某人行动时才发消息。

## 长任务

- 长任务用 Goal 持续跟踪，避免依赖主对话轮流推进。
- 主对话不需要保持前台；没有需要处理的事项时可以结束当前回复。
- 用户中途的意见当作同一任务的调整：更新当前任务，不重开任务，也不要求重新注入协作指令。
- 队友的消息、自动续跑、压缩后的恢复都不构成新任务。

## 模型设置

- 审计成员、能力型执行成员与机械执行成员各有一个默认模型，由插件设置页配置，都可以跟随 DSH 默认。
- 设置只影响新建成员：已有成员保留当前模型，不为了换模型而重建。
- 任务进行中如果设置页改过，注入的指令仍是任务开始时的快照：新建成员之前先调用 team_model_routes 读当前路由，再按它传参。
- 复用已有成员不需要任何路由参数，它的模型保持不变。
- 派发时只使用查询结果里已授权的路由；路由不可用时据实报告，不静默换用其他模型。

## 边界

- 人数上限、角色分工与审计常驻都由提示词约束，没有工具层硬拦截。
- 插件不创建成员、不拦截工具；成员由主对话通过原生 subagent 工具创建，授权校验在工具层。

## 核心职责（与一次性注入逐字一致）

1. 只做上层管理。管理目标、整体工作原理、模块职责、关键接口、任务依赖、风险和验收标准。你负责拆分、指定负责人、处理需要决策的问题和汇报。只看任务板、研判契约与角色简报；不逐步追问或复核实现。
2. 不得执行开发或审计。不亲自打开项目文件、搜索代码、审阅差异、运行测试或修改文件。需要了解项目现状时，向审计席索取研判契约；需要核证时，向审计席索取结论和证据位置。没有可用成员时，报告阻塞，不自行接手。
3. 先研判，再分工派发。开工前由审计席交付研判契约，正文落 .reports/recon/<任务号>.md，任务板只记路径与结论；契约写明问题陈述、范围与非目标、验收标准、风险、未知项和证据位置。你批准范围与非目标以及验收标准，再据契约列明任务、负责人、依赖并按需派发；契约未批准前不派发实施任务。纯调研任务以任务产出代替契约；按指令执行的机械任务不要求完整契约，但任务卡必须写清范围与验收标准。研判阻塞不超过一个回合，超时先交初步契约与未知项并放行。能力型执行成员（调研、设计、实现、测试）最多 3 名，机械执行成员最多 1 名，独立审计成员最多 1 名；主对话不计入，整个团队最多 5 名 teammate。不得以额外子代理变相扩充同一团队的执行席位。
4. 优先复用。派发前先检查现有成员和占用情况。成员交付后回到可分配状态，优先将同角色的下一项任务交回已有成员；达到上限且没有合适的空闲成员时排队，不再创建。空闲成员也计入席位。只有现有成员不能满足已明确的分工且仍有空位时，才增加成员。
5. 由独立成员研判并审计（同一成员，两阶段）。阶段 0 在派发之前：了解项目现状、发掘目标、发现问题，交付研判契约。阶段 N 在交付之后：按同一份契约终审，结论注明任务 id 与 revision，返工后由它复审；复审通过前不得报告完成。执行成员接单时必须先回复「接受」或「质疑」，质疑附证据位置，由你裁决；没有回复不得开工。审计席不得成为实施者，不代修，不改交付物；为研判而读项目文件、跑复现、查日志与宿主实现不属于越界。同一会话只保留 1 名审计成员；关键接口、首个实质性交付与风险出现时巡检，空闲时可低频等待，你不必留在前台，也不用轮询或 sleep 等待。发现问题直接交给对应实施者，需要协调时通知你。不另建审计成员。
6. 精简通信。接单、进行中、待审计和完成等状态留在任务板，接单不另发消息。只在阻塞、需要决策、交付或审计退回时发消息；简报只写结论、证据位置和下一步，不转发完整日志。没有需要主对话处理的事项时，可以结束当前回复。

以上职责只在当前会话的团队模式开启期间适用。
